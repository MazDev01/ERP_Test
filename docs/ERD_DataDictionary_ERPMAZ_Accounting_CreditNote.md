# บันทึกคำตัดสินที่ถูกยกเลิก — ใบลดหนี้ ใบเพิ่มหนี้ และการคืนเงิน (โครงสร้างข้อมูล)
## ระบบ ERP MAZ — โมดูลบัญชี (Accounting Module) · **เอกสารฉบับนี้ไม่ใช่ข้อกำหนดของระบบแล้ว**
บริษัท ไอเมซเมกเกอร์ จำกัด | เขียน 24 ก.ย. 2569 (เช้า) · **ยกเลิกทั้งฉบับ 24 ก.ย. 2569 (บ่าย)**

> # ⛔ อย่านำเอกสารฉบับนี้ไปพัฒนา
>
> **วันที่ยกเลิก** — 24 ก.ย. 2569 วันเดียวกับที่เขียน
>
> **สิ่งที่เคยตัดสินไว้ในฉบับนี้** — เพิ่มสามตารางในโมดูลบัญชี คือ `credit_note` (ใบลดหนี้) `debit_note` (ใบเพิ่มหนี้) และ `refund` (การคืนเงิน) พร้อมความสัมพันธ์ 15 แถว ชุดเลขที่เอกสาร `CN` `DN` `RF` ขั้นอนุมัติของผู้บริหารก่อนออกเลขที่ และกฎ AC-BR-10 ถึง AC-BR-25
>
> **เหตุที่ยกเลิก** — เจ้าของระบบถามว่าใบลดหนี้มีไว้ทำอะไร ฟังคำอธิบายแล้วตัดสินว่า **บริษัทไม่ได้ทำงานแบบนั้น** เอกสารกลับรายการทั้งหมดออกจากโปรแกรมบัญชีของฝ่ายบัญชีเอง ไม่ใช่จากระบบนี้ ระบบจึงกลับไปใช้โครงสร้างเดิมตามที่ออกแบบไว้แต่แรก — ยกเลิกดีลหลังรับชำระโดยระบุเหตุผล ยกเลิกใบแจ้งหนี้ที่ยังไม่ชำระตาม ใบเสร็จที่ออกไปแล้วยังอยู่ และ **บริษัทไม่คืนเงินทุกกรณี**
>
> **ฉบับที่ใช้จริงตอนนี้** — `ERD_DataDictionary_ERPMAZ_Accounting.docx` (เอกสารหลัก) + `ERD_DataDictionary_ERPMAZ_Accounting_CancelDeal.md` (ส่วนเพิ่มเติมที่ใช้แทนไฟล์นี้)
>
> **เลขกฎ AC-BR-10 ถึง AC-BR-25 ปลดระวางแล้ว** ห้ามนำกลับมาใช้กับกฎเรื่องอื่น ถ้าเปิดเรื่องนี้ใหม่ให้คืนเลขเดิมตามความหมายเดิม
>
> **ทำไมยังเก็บไฟล์นี้ไว้** — โค้ดของทั้งสามเรื่องยังอยู่ในโปรเจค (พักไว้ ไม่ได้ลบ ดูหมายเหตุหัวส่วนใน `src/lib/acc-data.ts`) ถ้าฝ่ายบัญชีหรือผู้สอบบัญชีทักท้วง เรื่องนี้เปิดใหม่ได้ และรายละเอียดที่ตัดสินกันไว้อยู่ครบในไฟล์นี้

# เนื้อหาของฉบับที่ถูกยกเลิก (เก็บไว้อ้างอิงเท่านั้น)

> ทุกหัวข้อตั้งแต่บรรทัดนี้ลงไปเป็นข้อความเดิมของฉบับที่ถูกยกเลิก เก็บไว้ตามเดิมโดยไม่แก้ เพื่อให้เปิดเรื่องใหม่ได้ทันทีถ้าต้องกลับมาใช้ · **คำว่า "ต้องแก้ในเอกสารหลัก" ในหัวข้อข้างล่างไม่มีผลแล้ว ห้ามทำตาม**

## 0. สิ่งที่เปลี่ยนจากฉบับร่างก่อนหน้า (อ่านก่อน)

### 0.1 รอบแรก — คำตัดสินของเจ้าของระบบ 24 ก.ย. 2569

ฉบับร่างแรกสุดเขียนไว้ตอนที่กติกาหลายข้อยังไม่ตัดสิน ข้อความเดิมต่อไปนี้ **ผิดและถูกยกเลิก** ห้ามอ้างอิงต่อ

| ข้อความในฉบับร่างเดิม (ยกเลิก) | กติกาที่ใช้แทน |
| --- | --- |
| "ระบบรุ่นแรกออกได้เต็มจำนวนเท่านั้น" (AC-BR-12 เดิม) | ลดหนี้บางส่วนได้ ใบลดหนี้ระบุยอดที่ลดจริง อ้างใบกำกับภาษี/ใบแจ้งหนี้ต้นทาง และระบุเหตุผล (AC-BR-12 ใหม่) |
| "ถ้าออกผิดต้องออกใบแจ้งหนี้ใหม่" · "ยังไม่ทำใบเพิ่มหนี้ในรุ่นแรก" (AC-BR-13 เดิม) | ออกใบลดหนี้ผิดต้องแก้ด้วย **ใบเพิ่มหนี้ (debit note)** ที่อ้างใบลดหนี้ใบนั้นและระบุเหตุผล ห้ามลบ ห้ามแก้ ห้ามยกเลิกเลขที่เอกสารภาษีย้อนหลัง (AC-BR-13 ใหม่ + ตาราง `debit_note`) |
| "การคืนเงินทำนอกระบบ บันทึกที่ `refund_note` อย่างเดียว" (AC-BR-14 เดิม) | การคืนเงินเป็น **ระเบียนของตัวเอง** ในตาราง `refund` มีวันที่โอน ยอดที่โอน และหลักฐานการโอน แยกจากใบลดหนี้ (AC-BR-14 ใหม่) |
| ฟิลด์ `refund_needed` และ `refund_note` ในตาราง `credit_note` | ถอดออกทั้งคู่ แทนด้วยตาราง `refund` (ส่วนฟิลด์ `settle_mode` ที่เคยเสนอไว้ ถูกถอดออกอีกชั้นหนึ่ง — ดูข้อ 0.2) |
| "ไม่มีฟิลด์สถานะ เพราะใบลดหนี้ที่ออกแล้วยกเลิกไม่ได้" | ใบลดหนี้มีฟิลด์สถานะ เพราะต้องผ่าน **การอนุมัติของผู้บริหารก่อนออกเลข** เลขที่ออกเมื่ออนุมัติแล้วเท่านั้น และเลขที่ออกแล้วยังคงห้ามยกเลิกตามเดิม (AC-BR-19, AC-BR-23) |
| "รุ่นแรกไม่ต้องอนุมัติ แต่ให้ขึ้นการแจ้งเตือนถึงผู้บริหาร" | **ผู้บริหาร (CEO) ต้องอนุมัติก่อนออกเอกสารเสมอ** — ดูกติกาเดียวข้อ 0.2 |
| "ยกเลิกดีลหลังรับเงินแล้วไม่คืนเงิน" (ข้อความท้าย AC-BR-07 ในเอกสารหลัก) | ยังไม่คืนเงินโดยอัตโนมัติ แต่ **ไม่ใช่ข้อห้ามอีกต่อไป** — คืนเงินได้เมื่อมีใบลดหนี้ที่อนุมัติแล้วรองรับ และผู้บริหารอนุมัติการคืนเงินนั้น (AC-BR-21) |

### 0.2 รอบสอง — คำตัดสินเพิ่มเติมของเจ้าของระบบ

**คำตัดสินที่ 1 — ใบเพิ่มหนี้ต้องผ่านผู้บริหารด้วย · กติกาเดียวใช้กับทั้งสามเอกสาร**

> **การแก้เอกสารภาษีที่ออกไปแล้ว หรือการทำให้เงินออกจากบริษัท ต้องผ่านการอนุมัติของผู้บริหาร (CEO) ก่อนเสมอ — ใบลดหนี้ ใบเพิ่มหนี้ และการคืนเงิน เหมือนกันทั้งสามชนิด ไม่มีข้อยกเว้นและไม่มีเพดานยอด**

เจ้าของระบบอธิบายว่าที่ระบุไว้ครั้งก่อนเพียงสองเอกสาร เป็นเพราะตอนนั้นยังไม่ได้พูดถึงใบเพิ่มหนี้ ไม่ใช่เพราะตั้งใจยกเว้น ใบเพิ่มหนี้เรียกเก็บลูกค้าเพิ่มหลังจากเอกสารภาษีออกไปแล้ว กระทบลูกค้าโดยตรง และตามปกติเกิดจากความผิดพลาดของบริษัทเอง จึงต้องมีคนสองคนเห็นก่อน

ผลที่ตามมา — ข้อความเดิมในเอกสารฉบับก่อนที่ **ผิดและถูกยกเลิก**

| ข้อความที่ยกเลิก | กติกาที่ใช้แทน |
| --- | --- |
| ความเห็นในโค้ด `acc-data.ts` ที่ว่าใบเพิ่มหนี้ "ออกโดยฝ่ายบัญชีและได้เลขที่ทันที … จึงไม่เข้าเงื่อนไขที่ผู้บริหารต้องอนุมัติ" | ใบเพิ่มหนี้ต้องผ่านผู้บริหารเหมือนใบลดหนี้ และได้เลขที่ตอนอนุมัติเท่านั้น (AC-BR-19) |

**คำตัดสินที่ 2 — สามตาราง ไม่ใช่สองตาราง**

เจ้าของระบบยืนยันว่าเลข "สองตาราง" ครั้งก่อนเป็นการพูดพลาดของเขาเอง (นับใบลดหนี้กับการคืนเงิน แล้วพูดถึงใบเพิ่มหนี้ต่อในย่อหน้าเดียวกัน) เขาบอกว่าการรวมใบลดหนี้กับใบเพิ่มหนี้เป็นตารางเดียวแล้วเพิ่มคอลัมน์ชนิดเอกสารก็สมเหตุสมผล เพราะรูปร่างข้อมูลเกือบเหมือนกัน แต่ในเมื่อระบบที่พัฒนาแล้วแยกเป็นสามชุด **ให้คงสามตารางไว้** ข้อดีคือเลขที่เอกสารของแต่ละชนิดเป็นคนละชุดชัดเจน · ประเด็น "จำนวนตาราง" จึงถูกถอดออกจากหัวข้อ 8 แล้ว

### 0.3 รอบสอง — จุดที่เอกสารฉบับก่อนไม่ตรงกับระบบที่พัฒนาแล้ว (แก้ตามโค้ด)

โค้ดจริงอยู่ที่ `src/lib/acc-data.ts`, `src/lib/acc-store.ts`, `src/components/acc-credits-page.tsx`, `src/components/acc-doc.tsx`, `src/components/ceo-approvals-page.tsx` และ `src/lib/system-settings.ts` · **ยึดโค้ดเป็นของจริง** ข้อความเดิมต่อไปนี้ถูกแก้แล้วในเอกสารฉบับนี้

| หัวข้อ | ฉบับก่อน (ยกเลิก) | ของจริงในระบบ |

| ฟิลด์เหตุผลที่ตีกลับ | `reject_reason` | `comment` (ฟิลด์เดียว ใช้เก็บเหตุผลที่ผู้บริหารตีกลับ) |

| `is_partial` | มีเป็นฟิลด์ | ไม่เก็บ คิดเอาจากยอด (`creditRoom()`) ตอนแสดงผล |

| คีย์ที่ใช้อ้างถึงกัน | คีย์นอกเป็น `BIGINT` ชี้ `*_id` | ในโปรแกรมหน้าบ้านอ้างกันด้วย **เลขที่เอกสาร** (`inv`, `receipt`, `credit`) และรหัสดีล/ชื่อลูกค้าเป็นข้อความ · ตารางข้างล่างจึงมีทั้งคอลัมน์ฐานข้อมูล (สำหรับตอนต่อฐานข้อมูลจริง) และคอลัมน์ชื่อฟิลด์ในโค้ด |
| ตาราง `refund` | มี `receipt_id`, `bank_account`, `transfer_date` แยกจากวันอนุมัติ, `paid_by`/`paid_at`, `note`, สถานะ `paid` | **ไม่มีทั้งหมด** · มี `paidDate` (วันที่โอนคืน) `method` (ช่องทางเป็นข้อความอิสระ) และ `evidence` (หลักฐานเป็นข้อความ) ซึ่งฝ่ายบัญชีกรอก **ตั้งแต่ตอนส่งขออนุมัติ** และไม่มีสถานะ `paid` |

## 1. เหตุที่ต้องมีตารางเหล่านี้

ก่อนหน้านี้เมื่อยกเลิกดีลที่ออกใบแจ้งหนี้ไปแล้ว ระบบเพียงเปลี่ยนสถานะใบแจ้งหนี้เป็น `cancelled` และตัดยอดค้างเป็นศูนย์ ใบแจ้งหนี้ที่ออกเลขและส่งให้ลูกค้าไปแล้วจึงหายไปเงียบ ๆ โดยไม่มีเอกสารใดกลับรายการ ซึ่งขัดกับกติกาเอกสารของระบบที่ว่า **เอกสารที่ออกเลขแล้วห้ามลบและห้ามยกเลิกเพื่อออกใหม่**

เจ้าของระบบตัดสินว่าต้องมีเอกสารกลับรายการครบทั้งสามทาง และ **แยกเป็นสามตาราง** (คำตัดสินที่ 2)

1. **ใบลดหนี้ (credit note)** — ลดยอดตามใบกำกับภาษี/ใบแจ้งหนี้ที่ออกไปแล้ว ลดได้ทั้งใบหรือบางส่วน เช่น ลูกค้ายกเลิกงาน ยกเลิกดีล หรือเรียกเก็บเกิน ใบลดหนี้ระบุยอดที่ลด อ้างเลขที่เอกสารต้นทาง และระบุเหตุผล
2. **ใบเพิ่มหนี้ (debit note)** — ใช้แก้ใบลดหนี้ที่ออกผิด เพราะเลขที่เอกสารภาษีที่ส่งออกไปแล้วยกเลิกย้อนหลังไม่ได้ ใบเพิ่มหนี้ **อ้างทั้งใบลดหนี้ที่แก้และใบกำกับภาษี/ใบแจ้งหนี้ต้นทางเดิมพร้อมกัน** และระบุเหตุผล
3. **การคืนเงิน (refund)** — เงินที่ออกจากบัญชีบริษัทจริง แยกจากใบลดหนี้ เพราะใบลดหนี้ลดภาระภาษีและยอดลูกหนี้ ส่วนการคืนเงินคือเงินไหลออก สองอย่างนี้ไม่ได้เกิดพร้อมกันเสมอ

**ทั้งสามชนิดต้องผ่านการอนุมัติของผู้บริหารก่อนออกเลขที่เอกสาร ไม่มีข้อยกเว้นและไม่มีเพดานยอด (AC-BR-19)**

## 1.1 กลุ่มข้อมูลและตารางที่เกิดขึ้น (แถวที่ต้องแก้ในเอกสารหลัก)

| กลุ่มข้อมูล | ตารางที่เกิดขึ้น |

## 1.2 เลขที่เอกสารในโมดูลนี้ (ข้อความที่ต้องแก้ในเอกสารหลัก)

เอกสารที่ออกเลขในโมดูลนี้คือใบแจ้งหนี้ ใบเสร็จรับเงิน **ใบลดหนี้ ใบเพิ่มหนี้ และใบสำคัญจ่ายคืนเงิน** ใช้รูปแบบเดียวกันทั้งหมด คือ ตัวย่อ + ปี ค.ศ. สองหลัก + ขีด + เดือนสองหลัก + ลำดับสี่หลัก (ฟังก์ชัน `nextAccDocNo()`)

| เอกสาร | ตัวนำหน้าตั้งต้น | คีย์ในค่าตั้งค่า (`DocPrefixes`) | ตัวอย่าง | เป็นเอกสารภาษี |
| --- | --- | --- | --- | --- |
| ใบแจ้งหนี้ | `INV` | `invoice` | `INV26-090014` | ใช่ |
| ใบเสร็จรับเงิน | `RCP` | `receipt` | `RCP26-090007` | ใช่ |
| ใบลดหนี้ | `CN` | `creditNote` | `CN26-090001` | ใช่ |
| ใบเพิ่มหนี้ | `DN` | `debitNote` | `DN26-090001` | ใช่ |
| ใบสำคัญจ่ายคืนเงิน | `RF` | `refund` | `RF26-090001` | ไม่ใช่ (เอกสารภายใน) |

ค่าตั้งต้นทั้งห้าอยู่ที่ `DEFAULT_SETTINGS.docs` ใน `src/lib/system-settings.ts` ผู้ดูแลระบบแก้ได้ที่หน้าเลขที่เอกสาร (`/admin/doc-numbers`) และระบบอ่านผ่าน `settings()` เสมอ ไม่เก็บเป็นค่าคงที่ในโค้ดที่ออกเลข

**การนับลำดับ** — นับจากเลขที่มากที่สุดของเดือนนั้นที่มีอยู่แล้วในชุดเดียวกัน เดินหน้าอย่างเดียว ไม่ซ้ำและไม่ข้าม เอกสารที่ออกเลขแล้วลบไม่ได้ · แต่ละชนิดนับแยกชุดของตัวเอง (ใบลดหนี้นับจากเลขใบลดหนี้ ใบเพิ่มหนี้นับจากเลขใบเพิ่มหนี้) ซึ่งเป็นข้อดีของการแยกสามตาราง

**จังหวะการออกเลข (ต่างจากใบแจ้งหนี้และใบเสร็จ)** — ใบลดหนี้ ใบเพิ่มหนี้ และใบสำคัญจ่ายคืนเงินต้องผ่านการอนุมัติก่อน ระบบจึงออกเลขให้ **ตอนที่ผู้บริหารกดอนุมัติ** ไม่ใช่ตอนที่ฝ่ายบัญชีกดส่ง คำขอที่ยังไม่อนุมัติไม่มีเลขที่ จึงแก้ได้ ไม่กินเลขในลำดับ และเลขที่ไม่ขาดช่วงเมื่อผู้บริหารตีกลับ (AC-BR-23)

> ⚠️ **จุดที่โค้ดยังไม่ตรง** — ปัจจุบัน `issueDebitNote()` ออกเลขใบเพิ่มหนี้ให้ทันทีที่ฝ่ายบัญชีกดออก ต้องแก้ให้เป็นสายอนุมัติเดียวกับใบลดหนี้ตามคำตัดสินที่ 1

รวมความสัมพันธ์ในโมดูลบัญชีจาก 13 เป็น **28** ความสัมพันธ์ (เพิ่ม 15 แถว) · ฉบับก่อนนับไว้ 24 เพราะยังไม่ได้นับ deal/customer ของใบเพิ่มหนี้และการคืนเงิน และยังนับความสัมพันธ์ `credit_note → payment_plan` (หักกลบงวดถัดไป) ซึ่งถูกถอดออกแล้วเพราะระบบยังไม่ทำ

**หมายเหตุเรื่องคีย์** — ในโปรแกรมหน้าบ้านปัจจุบัน ความสัมพันธ์ทั้งหมดผูกด้วย **เลขที่เอกสาร** (`inv`, `receipt`, `credit`), รหัสดีล (`deal`) และชื่อลูกค้า (`cus`) เป็นข้อความ ส่วนผู้ใช้เก็บเป็นชื่อบทบาท (`"ฝ่ายบัญชี"` / `"ผู้บริหาร"`) ยังไม่ได้ผูกกับตารางบัญชีผู้ใช้ เมื่อขึ้นฐานข้อมูลจริงให้เปลี่ยนเป็นคีย์นอกตามคอลัมน์ "ฟิลด์ (ฐานข้อมูล)" ในหัวข้อ 5.9–5.11

## 5.9 credit_note — ใบลดหนี้ *(ยกเลิกแล้ว · ไม่มีตารางนี้ในระบบ)*

**กลุ่มข้อมูล: A1** · ชนิดข้อมูลในโค้ด: `CreditNote` (`src/lib/acc-data.ts`)

เอกสารที่ออกเพื่อลดยอดตามใบแจ้งหนี้/ใบกำกับภาษีที่ออกเลขไปแล้ว เกิดขึ้นเมื่อยกเลิกดีลที่มีใบแจ้งหนี้ค้างอยู่ เมื่อปรับลดยอด/เรียกเก็บเกิน หรือเมื่อออกเอกสารผิด ใบลดหนี้อ้างใบแจ้งหนี้ได้ใบเดียว แต่ใบแจ้งหนี้หนึ่งใบมีใบลดหนี้ได้หลายใบจนกว่ายอดสะสมจะครบยอดตามใบ

ยอดในใบลดหนี้แยกบรรทัดเหมือนใบแจ้งหนี้ (ชนิดร่วม `TaxLines`) เพราะต้องพิมพ์ฐานภาษี ภาษีมูลค่าเพิ่ม และภาษีหัก ณ ที่จ่ายให้ครบตามเอกสารต้นทาง ระบบถอดยอดที่ลดตามสัดส่วนของใบแจ้งหนี้ต้นทางด้วย `invoiceAmounts()` ไม่คิดภาษีใหม่ · ระเบียนเกิดตอนฝ่ายบัญชีกดส่งขออนุมัติและยังไม่มีเลขที่ ผู้บริหารอนุมัติแล้วจึงออกเลข ออกเลขแล้วแก้ไม่ได้และยกเลิกไม่ได้ ต้องแก้ด้วยใบเพิ่มหนี้

| ฟิลด์ (ฐานข้อมูล) | ฟิลด์ในโค้ด | ชนิดข้อมูล | คีย์ | ค่าว่าง | คำอธิบาย |

**ข้อสังเกตด้านโครงสร้าง**

- ใบแจ้งหนี้ไม่เพิ่มสถานะใหม่ การถูกลดหนี้อนุมานจากการมีระเบียน `credit_note` ที่ `status = issued` เช่นเดียวกับที่สถานะชำระแล้วอนุมานจากการมีใบเสร็จ (AC-BR-05)
- ยอดที่ใบลดหนี้ใบหนึ่งลดจริง = `total` ของใบนั้น − Σ ใบเพิ่มหนี้ที่แก้ใบนั้น (ฟังก์ชัน `creditNet()`)
- ยอดลดหนี้สุทธิของใบแจ้งหนี้หนึ่งใบ = Σ `creditNet()` ของใบลดหนี้ที่ `issued` (ฟังก์ชัน `creditedTotal()`)
- ยอดที่ยังลดได้ของใบแจ้งหนี้ = ยอดตามใบ (`invoice.total`) − ยอดลดหนี้สุทธิ − **ยอดของใบที่ยังรออนุมัติ** (ฟังก์ชัน `creditRoom()`) การกันยอดของใบที่รออนุมัติทำให้ยอดขยับไม่ได้ระหว่างรอ จึงไม่ต้องเก็บ `approved_total` (แก้ AC-BR-24)
- **ยอดค้างชำระของใบแจ้งหนี้ลดลงด้วย `base + vat` ไม่ใช่ `total`** เพราะยอดค้าง (`invoice.outstanding`) คิดก่อนหักภาษี ณ ที่จ่ายตามกติกาเดิมของใบแจ้งหนี้ ส่วนเพดานการลดหนี้เทียบกับ `invoice.total` ซึ่งเป็นยอดฝั่งลูกค้า ทั้งสองชุดตัวเลขจึงไม่ปนกัน
- ใบที่ถูกตีกลับ (`returned`) ยังไม่มีเลขที่ จึงแก้ยอดและเหตุผลแล้วส่งใหม่ได้ (`resubmitCreditNote()`) ไม่ต้องสร้างระเบียนใหม่ เหตุผลที่ตีกลับเก็บที่ `comment` ให้ฝ่ายบัญชีเห็นบนป้ายสถานะ · ใบที่ตีกลับไม่กันยอดใน `creditRoom()`
- ยกเลิกดีล (`cancelDealBilling()`) ระบบตั้งคำขอใบลดหนี้เต็มยอดที่ยังลดได้ให้ใบแจ้งหนี้ทุกใบที่ยังค้าง โดยใช้ `reasonCode = deal_cancel` และเหตุผลเดียวกับที่บันทึกไว้ในดีล ยอดค้างลดตอนอนุมัติ ไม่ใช่ตอนกดยกเลิก
- ระบบยังไม่มีฟิลด์วิธีชดเชย (`settle_mode`) และไม่มีการหักกลบกับงวดถัดไป — ดูหัวข้อ 8

## 5.10 debit_note — ใบเพิ่มหนี้ *(ยกเลิกแล้ว · ไม่มีตารางนี้ในระบบ)*

**กลุ่มข้อมูล: A1** · ชนิดข้อมูลในโค้ด: `DebitNote` (`src/lib/acc-data.ts`)

เอกสารที่ออกเพื่อแก้ใบลดหนี้ที่ออกผิด เพราะเลขที่เอกสารภาษีที่ส่งออกไปแล้วยกเลิกย้อนหลังไม่ได้ ใบเพิ่มหนี้เพิ่มยอดหนี้กลับเข้าใบแจ้งหนี้เดิมเท่าที่ลดผิดไป และระบุเหตุผลทุกครั้ง

**ใบเพิ่มหนี้อ้างถึงเอกสารสองใบพร้อมกันเสมอ** — `credit` คือใบลดหนี้ที่ใบนี้แก้ และ `inv` คือใบกำกับภาษี/ใบแจ้งหนี้ต้นทางเดิมที่ยอดจะถูกเพิ่มกลับเข้าไป การเก็บทั้งสองทางทำให้คิดยอดค้างของใบแจ้งหนี้ได้โดยไม่ต้องไล่ผ่านใบลดหนี้ และให้เอกสารที่พิมพ์ออกมาอ้างต้นทางได้ครบตามที่สรรพากรต้องการ

**ข้อสังเกตด้านโครงสร้าง**

- **สามตาราง ไม่ใช่สองตาราง** (คำตัดสินที่ 2) — เจ้าของระบบรับว่าการรวมใบลดหนี้กับใบเพิ่มหนี้เป็นตารางเดียวแล้วเพิ่มคอลัมน์ชนิดเอกสารก็สมเหตุสมผล เพราะรูปร่างข้อมูลเกือบเหมือนกัน แต่ให้คงสามตารางตามที่ระบบทำไว้แล้ว ข้อดีคือเลขที่เอกสารของแต่ละชนิดเป็นคนละชุดชัดเจน · ประเด็นนี้ปิดแล้ว ไม่อยู่ในหัวข้อ 8 อีก
- ใบเพิ่มหนี้ในเอกสารนี้ใช้เพื่อ **แก้ใบลดหนี้** เท่านั้น ไม่ได้ใช้เรียกเก็บเพิ่มเพราะราคางานเพิ่ม กรณีนั้นออกใบแจ้งหนี้งวดใหม่ตามเดิม จึงบังคับว่าต้องมี `credit`
- ยอดเพิ่มหนี้รวมของใบลดหนี้ใบหนึ่งต้องไม่เกินยอดที่ใบนั้นลดไว้ เพิ่มเกินกว่านั้นคือสร้างหนี้ใหม่ ไม่ใช่การแก้
- ยอดค้างของใบแจ้งหนี้กลับคืนมาเท่ากับ `base + vat` ของใบเพิ่มหนี้ แต่ไม่เกินยอดเต็มของใบแจ้งหนี้ (`invoice.base + invoice.vat`)
- ใบเพิ่มหนี้ไม่ทำให้เงินไหลเข้าเอง ถ้าลูกค้าต้องจ่ายเพิ่มจริง ยอดจะกลับไปเป็นยอดค้างของใบแจ้งหนี้เดิม แล้วรับชำระด้วยใบเสร็จตามปกติ
- ถ้าใบลดหนี้ที่ผิดมีการคืนเงินไปแล้ว ใบเพิ่มหนี้ไม่ดึงเงินกลับ ระเบียน `refund` เดิมคงอยู่ ยอดที่ต้องเรียกคืนกลายเป็นยอดค้างของใบแจ้งหนี้

> ⚠️ **สรุปสิ่งที่โค้ดต้องแก้ตามคำตัดสินที่ 1** — `DebitNote` ปัจจุบันไม่มีฟิลด์สถานะและฟิลด์ผู้อนุมัติเลย และ `issueDebitNote()` ออกเลขให้ทันที ต้องเปลี่ยนเป็น `requestDebitNote()` + `decideDebitNote()` คู่เดียวกับใบลดหนี้ เพิ่มชนิดคำขอ `debit` ในหน้าคำขออนุมัติของผู้บริหาร และเพิ่มการแจ้งเตือนชุดเดียวกัน · ความเห็นในหัวชนิด `DebitNote` ที่บอกว่าใบเพิ่มหนี้ไม่ต้องอนุมัติ ต้องลบออก

## 5.11 refund — การคืนเงิน *(ยกเลิกแล้ว · ไม่มีตารางนี้ในระบบ)*

**กลุ่มข้อมูล: A2** · ชนิดข้อมูลในโค้ด: `Refund` (`src/lib/acc-data.ts`)

เงินที่บริษัทโอนคืนลูกค้าจริง แยกจากใบลดหนี้เพราะใบลดหนี้ลดภาระภาษีและยอดลูกหนี้ ส่วนการคืนเงินคือเงินออกจากบัญชีบริษัท สองอย่างนี้ไม่ได้เกิดพร้อมกันเสมอ ระเบียนนี้เก็บวันที่โอน ยอดที่โอน ช่องทาง และหลักฐานการโอน และต้องผ่านการอนุมัติของผู้บริหาร

| ฟิลด์ (ฐานข้อมูล) | ฟิลด์ในโค้ด | ชนิดข้อมูล | คีย์ | ค่าว่าง | คำอธิบาย |

**ข้อสังเกตด้านโครงสร้าง**

- **ไม่มีฟิลด์ `receipt_id`, `bank_account`, `paid_by`, `paid_at`, `note` และไม่มีสถานะ `paid`** ตามที่ฉบับก่อนเขียนไว้ · บัญชีปลายทางรวมอยู่ในข้อความ `method` และ `evidence` ได้ ถ้าต้องแยกช่องจริงให้ยกเป็นงานรอบถัดไป (หัวข้อ 8)
- ใบลดหนี้หนึ่งใบมีการคืนเงินได้หลายครั้ง (ทยอยคืน) ยอดคืนสะสมของใบลดหนี้ใบหนึ่งต้องไม่เกินยอดที่ใบนั้นลดจริง (`creditNet()` − `refundedOf()`) · รายการที่ถูกตีกลับไม่นับรวม
- คืนเงินได้เฉพาะเมื่อใบแจ้งหนี้ของใบลดหนี้นั้น **มีใบเสร็จแล้วจริง** เงินที่ยังไม่เคยเข้าไม่มีอะไรให้คืน ใบลดหนี้ใบนั้นไปหักกับยอดค้างแทน
- การคืนเงินไม่แก้ใบเสร็จและไม่แก้รายการเงินรับ เพราะเงินเข้าแล้วจริง รายงานจึงต้องแยกสองบรรทัด คือ "ยอดรับเงินจริง" และ "ยอดคืนเงิน" แล้วค่อยหักกันที่ยอดเงินสดสุทธิ
- ระเบียนที่อนุมัติแล้ว (`issued`) แก้และลบไม่ได้ คืนผิดต้องบันทึกการรับเงินคืนเข้าเป็นรายการใหม่ ไม่ใช่ลบระเบียนเดิม
- ⚠️ **ลำดับเวลาที่ยังไม่ลงตัว** — โค้ดให้ฝ่ายบัญชีกรอกวันที่โอนและหลักฐานตั้งแต่ตอนส่งขออนุมัติ แปลว่าตามหน้าจอจริงเงินออกก่อนแล้วผู้บริหารจึงอนุมัติ ซึ่งกลับทางกับกติกา "อนุมัติก่อนโอน" ที่เขียนไว้ — ดูหัวข้อ 8

## 7. กฎทางธุรกิจที่ผูกกับโครงสร้างข้อมูล (แถวที่ต้องเพิ่ม) *(AC-BR-10 – AC-BR-25 ปลดระวางทั้งช่วง)*

> **ไม่มีการเปลี่ยนเลขกฎในรอบนี้** — AC-BR-10 ถึง AC-BR-24 ยังเป็นเรื่องเดิมทุกข้อ · AC-BR-19 ขยายความให้ครอบคลุมทั้งสามชนิดตามคำตัดสินที่ 1 · AC-BR-22 ถูกพักเพราะระบบยังไม่ทำ · AC-BR-24 เขียนใหม่ให้ตรงกับวิธีที่ระบบกันยอดจริง · เพิ่ม AC-BR-25 เป็นข้อใหม่

## 8. ประเด็นที่ยังต้องยืนยันกับผู้ใช้ (แถวที่ต้องเพิ่ม)

ประเด็นเรื่องลดหนี้บางส่วน ใบเพิ่มหนี้ การคืนเงิน การอนุมัติของผู้บริหารทั้งสามชนิด และ **จำนวนตาราง (สามตาราง)** ตัดสินแล้วทั้งหมด ที่เหลือคือประเด็นที่ยังไม่ได้ตัดสินจริง ๆ

| ประเด็น | ข้อเสนอของผู้เขียนเอกสาร (รอเจ้าของระบบยืนยัน) |
| --- | --- |
| **ลำดับเวลาของการคืนเงิน — อนุมัติก่อนโอน หรือ โอนแล้วค่อยอนุมัติ** | กติกาเขียนว่า "ผู้บริหารอนุมัติก่อนเงินออก" แต่หน้าจอที่ทำแล้วบังคับให้ฝ่ายบัญชีกรอกวันที่โอนและหลักฐานการโอนตั้งแต่ตอนส่งขออนุมัติ ซึ่งแปลว่าโอนไปก่อนแล้ว · **ข้อเสนอ: ยึดกติกาเดิม คืออนุมัติก่อนโอน** โดยแยกเป็นสองขั้น — ตอนขอกรอกเพียงยอด ช่องทาง และวันที่ตั้งใจจะโอน อนุมัติแล้วจึงกลับมาบันทึกวันที่โอนจริงกับหลักฐาน แล้วเพิ่มสถานะที่สี่ (`paid`) · ถ้าเจ้าของระบบยืนยันว่าทำจริงแบบโอนก่อนแล้วให้ผู้บริหารรับรองทีหลัง ต้องแก้ถ้อยคำใน AC-BR-20 ให้ตรง ไม่ใช่ปล่อยให้เอกสารกับระบบพูดคนละอย่าง |
| **การหักกลบกับงวดถัดไป (เดิม `settle_mode` / AC-BR-22)** | ระบบยังไม่ทำเลย ใบลดหนี้ที่ยังไม่รับชำระหักกับยอดค้างของใบแจ้งหนี้โดยตรงอยู่แล้ว · **ข้อเสนอ: ยังไม่ต้องทำในรุ่นนี้** ถ้าจะทำต้องเพิ่มฟิลด์วิธีชดเชยและคีย์นอกไปยังงวด แล้วใบแจ้งหนี้ของงวดนั้นแสดงบรรทัด "หักกลบตามใบลดหนี้ CNxx-xxxxxx" โดยไม่แก้ยอดงวดในแผน |
| **ช่องบัญชีปลายทางของการคืนเงิน** | ตอนนี้รวมอยู่ในข้อความ `method` และ `evidence` · **ข้อเสนอ: แยกเป็นฟิลด์ `bank_account` เมื่อขึ้นฐานข้อมูลจริง** เพราะต้องใช้ตอนสอบทานการจ่ายเงิน แต่ยังไม่จำเป็นในรุ่นหน้าจอปัจจุบัน |
| **ช่องทางคืนเงินเป็นข้อความอิสระหรือค่าคงที่** | โค้ดเก็บเป็นข้อความอิสระ ค่าตั้งต้น "โอนเงินเข้าบัญชีลูกค้า" · **ข้อเสนอ: ทำเป็นดรอปดาวน์ (โอน / เช็ค / เงินสด) + ช่องกำหนดเอง** ตามแนวทางเดียวกับค่าตั้งค่าอื่นของระบบ เพื่อให้รายงานจัดกลุ่มได้ |
| **สาเหตุของใบเพิ่มหนี้** | ใบลดหนี้มี `reason_code` แต่ใบเพิ่มหนี้มีแต่ข้อความอิสระ · **ข้อเสนอ: เพิ่ม `reason_code` ให้ใบเพิ่มหนี้เป็นสามค่า** (`cn_amount_wrong` ยอดผิด, `cn_wrong_invoice` ลดหนี้ผิดใบ, `cn_not_needed` ไม่ควรลดตั้งแต่แรก) ให้เข้าคู่กับใบลดหนี้ และช่วยให้ผู้บริหารตัดสินใจเร็วขึ้น |
| ผู้อนุมัติสำรองเมื่อผู้บริหารไม่อยู่ | **ข้อเสนอ: ยังไม่ทำผู้อนุมัติสำรอง** ให้ผู้บริหารกดอนุมัติจากมือถือได้เหมือนคำขออื่น ถ้าจะทำต้องกำหนดที่หน้าสายอนุมัติเหมือนบทบาทอื่น (ปัจจุบันผู้จัดการทั่วไปดูได้อย่างเดียว) |
| ใบลดหนี้ย้อนหลังของข้อมูลเดิม | ทำแล้วหนึ่งใบ — `CN26-090001` ลดหนี้ `INV26-080031` ของดีล DL-2569-0017 ลงวันที่ที่ทำรายการจริง (6 ก.ย. 2569) ไม่ย้อนวันที่ · **ถ้ามีใบแจ้งหนี้เก่าที่ถูกตั้งเป็นยกเลิกไว้อีก ต้องไล่ออกให้ครบด้วยวิธีเดียวกัน** |
| ชื่อเอกสารที่พิมพ์ | ทำตามข้อเสนอเดิมแล้ว — ผูกกับการจดทะเบียนภาษีมูลค่าเพิ่มของผู้ออกผ่านค่า `ISSUER_VAT` และฟิลด์ `vatDoc` ผู้ใช้เลือกเองไม่ได้ · **รอเจ้าของระบบยืนยันว่าถ้อยคำบนหัวเอกสารถูกต้อง** ("ใบลดหนี้ / ใบกำกับภาษี" และ "ใบเพิ่มหนี้ / ใบกำกับภาษี") |
| รหัสยูสเคสและเลขหัวข้อ | ใช้ AC-01 ถึง AC-03 และหัวข้อ 3.3.1–3.3.3 ไปก่อน รอยืนยันเมื่อเขียนเอกสารยูสเคสโมดูลบัญชีเต็มฉบับ เนื่องจากปัจจุบันการวางบิลถูกอ้างในชื่อ SL-05 ของโมดูลงานขาย |
